\chapter*{Streszczenie}
\addcontentsline{toc}{chapter}{Streszczenie}

Praca pt.\ \textit{„Architektura mikroserwisów i~rozwiązania chmurowe w~ekosystemie .NET”} poświęcona jest projektowaniu, implementacji oraz empirycznej analizie wydajności systemu rozproszonego zbudowanego w~oparciu o~platformę .NET~10. W~ostatnim czasie obserwuje się intensywny rozwój protokołu gRPC jako alternatywy dla powszechnie stosowanego REST w~komunikacji między mikroserwisami. Jednocześnie środowisko przeglądarek internetowych wymaga stosowania wariantu \textit{gRPC-Web}, którego wydajność w~komunikacji klient--backend pozostaje słabo zbadana empirycznie. W~rozważanej pracy podjęto zatem próbę wypełnienia tej luki badawczej. W~szczególności zebrano wiadomości z~zakresu architektury mikroserwisów, mechanizmów komunikacji synchronicznej i~asynchronicznej oraz wzorców projektowych w~ekosystemie .NET, porównano trzy warianty komunikacji dostępne dla aplikacji przeglądarkowej: REST (HTTP/1.1 z~serializacją JSON), gRPC-Web przez proxy Envoy oraz gRPC-Web obsługiwany bezpośrednio w~ASP.NET Core, zrealizowano system testowy złożony z~dwóch mikroserwisów (\textit{ProductService} i~\textit{OrderService}), wdrożony na~serwerze chmury Hetzner, a~także opracowano metodykę pomiarową opartą na~rzeczywistej przeglądarce internetowej, w~której czas mierzony jest od~interakcji użytkownika do~naniesienia odpowiedzi na~drzewo dokumentu. Przeprowadzono 39~konfiguracji pomiarowych w~pięciu niezależnych powtórzeniach z~rotowaną kolejnością protokołów, co~dało 585~wykonanych testów i~171~tysięcy pomiarów, przy rozmiarach ładunku od~10 do~2000 rekordów oraz scenariuszach obejmujących izolowany narzut protokołu, odczyt katalogu i~zapis zamówienia. Zaprojektowany i~zaimplementowany system charakteryzuje się następującymi cechami: podejściem \textit{contract-first} opartym na~\textit{Protocol Buffers} zapewniającym silną typizację w~całym stosie technologicznym, kompleksową obserwowalnością obejmującą metryki (Prometheus, Grafana). Przeprowadzone badania wykazały, że~warianty gRPC-Web skracają czas odpowiedzi o~26--43\% względem REST, lecz wyłącznie przy nieskompresowanych odpowiedziach przekraczających rozmiar okna odbiorczego protokołu TCP; przy typowych ładunkach interfejsu użytkownika oraz w~operacjach zapisu różnice pozostają nieistotne. Wykazano ponadto, że~kompresja treści redukuje wolumen dokumentu JSON dwunasto- do~trzynastokrotnie i~sprowadza wszystkie badane ładunki poniżej rozmiaru jednego okna odbiorczego, co~wyznacza granicę stosowalności powyższego wniosku. Sformułowano model wyjaśniający tę~zależność liczbą wymian pakietów wynikającą z~wolumenu odpowiedzi, którego przewidywania zgadzają się z~pomiarem z~dokładnością do~0,2~obiegu pakietu. Wykazano ponadto, że~około 95\% obserwowanej przewagi wynika z~binarnej serializacji redukującej wolumen danych o~42--43\%, a~nie z~zastosowanej wersji protokołu HTTP, oraz że~korzyść ta~skaluje się z~opóźnieniem sieci, nie z~szybkością serwera.

\chapter*{Summary}
\addcontentsline{toc}{chapter}{Summary}

The thesis entitled \textit{``Microservices Architecture and Cloud Solutions in the .NET Ecosystem''} is devoted to the design, implementation, and empirical performance analysis of a distributed system built on the .NET~10 platform. Recently, rapid growth and adoption of the gRPC protocol have been observed as an alternative to the widely used REST for inter-microservice communication. At the same time, the web browser environment necessitates the use of the \textit{gRPC-Web} variant, whose performance in client--backend communication remains insufficiently investigated empirically. This study therefore aims to address and fill this research gap. In particular, the thesis synthesizes knowledge in microservices architecture, synchronous and asynchronous communication mechanisms, and design patterns within the .NET ecosystem; compares three communication variants available to web browser applications: REST (HTTP/1.1 with JSON serialization), gRPC-Web via an Envoy proxy, and gRPC-Web natively hosted in ASP.NET Core; implements a benchmark testbed consisting of two microservices (\textit{ProductService} and \textit{OrderService}) deployed on a Hetzner Cloud server; and establishes a measurement methodology based on a real web browser, where end-to-end latency is measured from the initial user interaction to the rendering of the response into the Document Object Model (DOM) tree. A total of 39~measurement configurations were executed across five independent repetitions with rotated protocol ordering, yielding 585~test runs and 171~thousand individual measurements, spanning payload sizes from 10 to 2000 records across scenarios covering isolated protocol overhead, catalog read, and order placement. The designed and implemented system is characterized by: a \textit{contract-first} approach based on \textit{Protocol Buffers} providing strong typing across the entire technology stack, and comprehensive observability encompassing metrics (Prometheus, Grafana). The empirical evaluation revealed that gRPC-Web variants reduce response times by 26--43\% compared to REST, but exclusively for uncompressed responses exceeding the initial TCP receive window size; for typical user interface payloads and write operations, the differences remain negligible. Furthermore, it was demonstrated that response compression reduces JSON document size by a factor of 12--13, bringing all evaluated payloads below the threshold of a single receive window, thereby defining the boundary of practical applicability for the aforementioned performance advantage. A model accounting for this relationship based on the number of network round-trips dictated by payload volume was formulated, with predictions aligning with empirical measurements within 0.2~packet round-trips. In addition, it was established that approximately 95\% of the observed performance gain is attributable to binary serialization reducing data volume by 42--43\%, rather than the underlying HTTP transport version, and that this benefit scales primarily with network latency rather than server compute capacity.
