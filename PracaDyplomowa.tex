\chapter*{Streszczenie}
\addcontentsline{toc}{chapter}{Streszczenie}

Praca pt.\ \textit{„Architektura mikroserwisów i~rozwiązania chmurowe w~ekosystemie .NET”} poświęcona jest projektowaniu, implementacji oraz empirycznej analizie wydajności systemu rozproszonego zbudowanego w~oparciu o~platformę .NET~10. W~komunikacji między mikroserwisami protokół gRPC bywa stosowany jako alternatywa dla powszechnego REST, ponieważ wykorzystuje binarną serializację danych oraz protokół HTTP/2. Jednocześnie środowisko przeglądarek internetowych wymaga stosowania wariantu \textit{gRPC-Web}, którego wydajność w~komunikacji klient--backend pozostaje słabo zbadana empirycznie. Praca uzupełnia tę~lukę eksperymentem przeprowadzonym w~rzeczywistej przeglądarce internetowej. W~części teoretycznej zebrano wiadomości z~zakresu architektury mikroserwisów, mechanizmów komunikacji synchronicznej oraz mechanizmów obecnych na~ścieżce żądania w~ekosystemie .NET, a~także omówiono dotychczasowe badania porównawcze protokołów REST, gRPC i~GraphQL wraz z~ograniczeniami przenoszalności ich wyników. Porównaniu poddano trzy warianty komunikacji dostępne dla aplikacji przeglądarkowej: REST (HTTP/1.1 z~serializacją JSON), gRPC-Web przez proxy Envoy oraz gRPC-Web obsługiwany bezpośrednio w~ASP.NET Core. Na~potrzeby pomiarów zrealizowano system testowy złożony z~dwóch mikroserwisów (\textit{ProductService} i~\textit{OrderService}), wdrożony na~serwerze chmury Hetzner oraz opracowano metodykę pomiarową opartą na~rzeczywistej przeglądarce internetowej, w~której czas mierzony jest od~interakcji użytkownika do~naniesienia odpowiedzi na~drzewo dokumentu. Przeprowadzono 36~konfiguracji pomiarowych w~pięciu niezależnych powtórzeniach z~rotowaną kolejnością protokołów, co~dało 540~wykonanych testów i~153~tysiące pomiarów, przy rozmiarach ładunku od~10 do~2000 rekordów oraz scenariuszach obejmujących izolowany narzut protokołu, odczyt katalogu i~zapis zamówienia. Zaprojektowany i~zaimplementowany system charakteryzuje się następującymi cechami: podejściem \textit{contract-first} opartym na~\textit{Protocol Buffers}, z~którego generowany jest kod serwera (C\#) i~klienta (TypeScript) dla ścieżek gRPC-Web oraz warstwą obserwowalności zgodną ze~standardem OpenTelemetry, obejmującą metryki eksportowane do~Prometheusa i~wizualizowane w~Grafanie. Przeprowadzone badania wykazały, że~warianty gRPC-Web skracają czas odpowiedzi o~26--43\% względem REST, lecz wyłącznie przy nieskompresowanych odpowiedziach przekraczających zaobserwowany w~badanym środowisku efektywny próg transmisji około 64~KiB; przy małych ładunkach różnice były niewielkie, a~w~operacjach zapisu nie wykryto stałej przewagi jednego wariantu. Brak rozstrzygnięcia różnic w~zapisie nie dowodzi równoważności protokołów. Analiza objętościowa wykazała, że~kompresja treści redukuje wolumen dokumentu JSON dwunasto- do~trzynastokrotnie i~sprowadza wszystkie badane ładunki poniżej efektywnego progu transmisji, co~wyznacza granicę stosowalności powyższego wniosku. Zależność tę~opisano modelem wiążącym czas odpowiedzi z~liczbą wymian pakietów wynikającą z~wolumenu danych; przewidywania modelu zgadzają się z~pomiarem z~dokładnością do~0,29~obiegu pakietu. Wykazano ponadto, że~różnica REST--Envoy stanowi około 85--98\% całkowitej różnicy REST--Direct w~pięciu analizowanych konfiguracjach, natomiast różnica między wariantami Envoy i~Direct była znacznie mniejsza. Ponieważ mechanizm ten opiera się na~liczbie zaoszczędzonych obiegów pakietu, skala korzyści zależy od~opóźnienia łącza, wobec czego wnioski odnoszą się do~komunikacji przez sieć rozległą. Na~podstawie wyników sformułowano rekomendacje architektoniczne oraz wytyczne wdrożeniowe, wskazujące rozmiar odpowiedzi po~kompresji, parametry łącza i~dominujący rodzaj operacji jako kryteria doboru mechanizmu komunikacji.

\chapter*{Summary}
\addcontentsline{toc}{chapter}{Summary}

The thesis entitled \textit{``Microservices Architecture and Cloud Solutions in the .NET Ecosystem''} is devoted to the design, implementation, and empirical performance analysis of a distributed system built on the .NET~10 platform. In inter-microservice communication, the gRPC protocol is used as an alternative to the widely adopted REST, as it relies on binary serialization and the HTTP/2 protocol. At the same time, the web browser environment necessitates the use of the \textit{gRPC-Web} variant, whose performance in client--backend communication remains insufficiently investigated empirically. This thesis addresses that gap through an experiment carried out in a real web browser. In particular, the thesis synthesizes knowledge in microservices architecture, synchronous communication mechanisms, and the mechanisms present on the request path within the .NET ecosystem; reviews existing comparative studies of REST, gRPC, and GraphQL together with the limitations on transferring their results; compares three communication variants available to web browser applications: REST (HTTP/1.1 with JSON serialization), gRPC-Web via an Envoy proxy, and gRPC-Web handled directly by ASP.NET Core; implements a benchmark testbed consisting of two microservices (\textit{ProductService} and \textit{OrderService}) deployed on a Hetzner Cloud server; and establishes a measurement methodology based on a real web browser, where end-to-end latency is measured from the initial user interaction to the moment the response is applied to the Document Object Model (DOM) tree. A total of 36~measurement configurations were executed across five independent repetitions with rotated protocol ordering, yielding 540~test runs and 153~thousand individual measurements, spanning payload sizes from 10 to 2000 records across scenarios covering isolated protocol overhead, catalog read, and order placement. The designed and implemented system is characterized by a \textit{contract-first} approach based on \textit{Protocol Buffers}, from which server code (C\#) and client code (TypeScript) for gRPC-Web paths are generated, and an observability layer compliant with the OpenTelemetry standard, encompassing metrics exported to Prometheus and visualized in Grafana. The empirical evaluation revealed that gRPC-Web variants reduce response times by 26--43\% compared to REST, but exclusively for uncompressed responses exceeding the effective transmission threshold of approximately 64~KiB observed in the experimental environment; for small payloads, differences were small, while write operations showed no consistent advantage for one variant. Inconclusive differences in write operations do not establish protocol equivalence. Furthermore, it was demonstrated that response compression reduces JSON document size by a factor of 12--13, bringing all evaluated payloads below the effective transmission threshold, thereby defining the boundary of practical applicability for the aforementioned performance advantage. A model accounting for this relationship based on the number of network round-trips dictated by payload volume was formulated, with predictions aligning with empirical measurements within 0.29~packet round-trips. In addition, it was established that the REST--Envoy difference accounts for approximately 85--98\% of the total REST--Direct difference across the five analysed configurations, whereas the difference between the Envoy and Direct variants was substantially smaller. Because the mechanism rests on the number of packet round-trips saved, the magnitude of the benefit depends on link latency, and the conclusions therefore apply to communication over a wide-area network. Building on these results, the thesis formulates architectural recommendations and deployment guidelines that identify the compressed response size, the link parameters, and the dominant operation type as the criteria for selecting a communication mechanism.
