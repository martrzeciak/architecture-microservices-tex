\chapter{Zrealizowany system i~jego wdrożenie}

\label{cha:StudiumPrzypadku}

W~rozdziale opisano system zrealizowany na~potrzeby pracy: jego architekturę, kontrakty usług, topologię kontenerów, implementację pamięci podręcznej istotną dla metodyki pomiaru, model wdrożenia w~środowisku chmurowym oraz warstwę obserwowalności.

% -----------------------------------------------------------------------
\section{Architektura badanego systemu testowego}
\label{sec:ArchitekturaSystemu}
% -----------------------------------------------------------------------

Na~potrzeby przeprowadzenia eksperymentów wydajnościowych zrealizowano autorski system testowy. Implementację podporządkowano celom badawczym, skupiając się na~porównaniu wybranych protokołów i~wariantów komunikacji sieciowej. Architektura systemu składa się z~trzech głównych warstw: warstwy prezentacji w~postaci aplikacji przeglądarkowej, warstwy usług biznesowych złożonej z~mikroserwisów opartych na~platformie .NET~10 oraz warstwy infrastrukturalnej obejmującej relacyjne bazy danych, pamięć podręczną i~komponenty obserwowalności.

Środowisko eksperymentalne zostało rozproszone pomiędzy dwie fizyczne maszyny: warstwa mikroserwisów wraz z~całą infrastrukturą pomocniczą została uruchomiona na~zewnętrznym serwerze, natomiast aplikacja kliencka działała lokalnie, na~stacji roboczej pełniącej rolę węzła pomiarowego.

Przyjęte podejście powinno zagwarantować, że~pomiary odzwierciedlają kompletną, rzeczywistą ścieżkę przetwarzania danych, uwzględniając opóźnienia sieciowe, warstwę pośredniczącą, routing, a~także procesy serializacji i~deserializacji realizowane przez silnik JavaScript w~przeglądarce internetowej.

\subsection{Warstwa usług biznesowych}
\label{subsec:WarstwaBiznesowa}

System realizuje podział na~dwa mikroserwisy zgodnie z~zasadą \textit{Bounded Context}~\cite{bib:Evans2003}:

\begin{itemize}
    \item \textbf{ProductService} (kontekst: katalog produktów) odpowiada za~operacje odczytu katalogu, implementuje wzorzec Cache-Aside oraz punkt końcowy izolujący narzut protokołu. Dane przechowywane w~dedykowanej bazie produktów obejmują 2000~produktów rozłożonych na~dziesięć kategorii.
    \item \textbf{OrderService} (kontekst: proces zamówień) odpowiada za~tworzenie
    zamówień: waliduje żądanie, zapisuje encję zamówienia wraz z~jego pozycjami. Dane przechowywane w~dedykowanej bazie zamówień.
\end{itemize}

Każdy mikroserwis jest autonomiczną jednostką wdrożeniową z~własnym obrazem kontenera, konfiguracją połączeń oraz migracjami bazy danych realizowanymi w~podejściu Code-First.

Istotną cechą przyjętego projektu jest całkowity brak zależności pomiędzy obiema usługami: nie występują ani synchroniczne wywołania, ani wymiana komunikatów pomiędzy \texttt{ProductService} a~\texttt{OrderService}. Decyzja ta~wynika bezpośrednio z~celu badawczego: przedmiotem pomiaru jest komunikacja na~granicy klient--usługa, a~nie orkiestracja procesu obejmującego wiele usług. Wprowadzenie zależności międzyusługowej wnosiłoby do~pomiarów opóźnienie drugiej usługi, utrudniając izolację narzutu samego protokołu. Konsekwencją takiego podziału jest pełna niezależność wdrożeniowa obu komponentów oraz brak sprzężenia.

\subsection{Podejście Contract-First}
\label{subsec:ContractFirst}

Kontrakty usług gRPC definiowane są~w~plikach Protocol Buffers, które stanowią wspólną definicję interfejsów systemowych. Na~ich podstawie generowany jest kod serwera (C\#, pakiet \texttt{Grpc.Tools}) i~klienta (TypeScript, narzędzia \texttt{@bufbuild/protoc-gen-es} oraz \texttt{@connectrpc/protoc-gen-connect-es}).
Podejście Contract-First umożliwia sprawdzanie zgodności typów na~granicy systemu podczas kompilacji. Część niekompatybilnych zmian można dzięki temu wykryć przed uruchomieniem aplikacji.

\section{Wdrożenie i~eksploatacja w~środowisku chmurowym}
\label{sec:WdrozenieChmurowe}
% -----------------------------------------------------------------------

System testowy wdrożono w~publicznej chmurze obliczeniowej, w~modelu infrastruktury jako usługi (ang.\ \textit{infrastructure as a~service}). Niniejsza sekcja przedstawia przyjęty model wdrożenia wraz z~jego uzasadnieniem, przebieg wdrożenia oraz warstwę obserwowalności. Rozstrzygnięcia omówione poniżej wynikają w~znacznej mierze z~wymagań eksperymentu.

\subsection{Uzasadnienie przyjętego modelu wdrożenia}
\label{subsec:ModelWdrozenia}

Wszystkie komponenty systemu uruchomiono jako kontenery na~pojedynczej instancji maszyny wirtualnej, zarządzane narzędziem Docker Compose w~konfiguracji przedstawionej w~tabeli~\ref{tab:DockerServices}. Rozwiązanie alternatywne, to~jest wdrożenie w~klastrze zarządzanym platformą Kubernetes wraz z~automatycznym skalowaniem poziomym odrzucono ze~względu na~wymagania pomiarowe.

Mechanizmy automatycznego skalowania oraz ponownego rozmieszczania kontenerów zmieniają liczbę i~lokalizację instancji w~czasie działania systemu. Stała topologia zapewniała powtarzalne warunki pomiaru. Badanie dotyczyło komunikacji, dlatego nie obejmowało wpływu platformy orkiestracji.

\subsection{Proces wdrożenia}
\label{subsec:Deployment}

System wdrożono na~serwerze chmury Hetzner Cloud o~ośmiu rdzeniach wirtualnych i~16~GB pamięci, z~wykorzystaniem Docker Compose w~konfiguracji wdrożeniowej. Proces wdrożenia obejmuje konfigurację serwera, weryfikację punktów końcowych gotowości każdego mikroserwisu oraz wykonanie automatycznych migracji bazy danych przy starcie usług.

Graf zależności Docker Compose określa kolejność uruchamiania kontenerów i~ogranicza liczbę przedwczesnych prób połączenia z~niedostępnymi usługami. Do~kontroli stanu służą punkty końcowe \texttt{/healthz/live} oraz \texttt{/healthz/ready}, udostępniane przez mechanizm wbudowany w~ASP.NET Core~\cite{bib:MicrosoftDocs2024}.

\section{Obserwowalność systemu}
\label{subsec:Observability}

System integruje dwa filary obserwowalności zgodnie ze~standardem OpenTelemetry~\cite{bib:OpenTelemetry2024}, obejmując: metryki eksportowane do~Prometheusa przez dedykowany punkt końcowy (czas odpowiedzi, liczba aktywnych połączeń oraz parametry środowiska uruchomieniowego .NET), a~także warstwę wizualizacji danych opartą na~platformie Grafana z~automatycznie wdrażaną konfiguracją źródeł oraz paneli analitycznych.

Pulpity Grafany wdrażane są~wraz z~całym stosem, w~postaci definicji przechowywanych w~repozytorium i~wczytywanych przy starcie kontenera. Dzięki temu warstwa wizualizacji odtwarzana jest automatycznie na~każdym środowisku, bez ręcznej konfiguracji. Pierwszy z~pulpitów (rysunek~\ref{fig:GrafanaHttp}) obejmuje charakterystykę warstwy HTTP obu mikroserwisów: liczbę żądań na~sekundę oraz percentyle czasu obsługi żądania mierzone po~stronie serwera. Drugi (rysunek~\ref{fig:GrafanaRuntime}) przedstawia rozbicie liczby żądań na~poszczególne trasy oraz metryki środowiska uruchomieniowego .NET: wolumen alokacji pamięci i~częstość usuwania zbędnych obiektów z pamięci aplikacji.

Przebiegi zarejestrowano podczas obciążeniowej weryfikacji stosu obserwowalności, poza właściwą macierzą badawczą. Ilustrują działanie warstwy monitorowania i~nie są~wynikami eksperymentu. Warstwa obserwowalności pełniła funkcję pomocniczą.
