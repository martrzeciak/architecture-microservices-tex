\chapter{Mechanizmy komunikacji w~architekturze mikroserwisowej}

\label{cha:MechanizmyKomunikacji}

Jak przedstawiono w~rozdziale~\ref{cha:WprowadzenieDoMikroserwisow}, architektura mikroserwisowa zakłada podział systemu na~niezależne usługi odpowiedzialne za~określone obszary funkcjonalne. Każdy mikroserwis funkcjonuje jako odrębny proces, co~sprawia, że~realizacja złożonych procesów biznesowych wymaga komunikacji pomiędzy poszczególnymi usługami. Wymiana danych przestaje być wówczas wywołaniem wewnątrz procesu i~staje się elementem, którego koszt obciąża czas obsługi każdej operacji~\cite{bib:Richardson2018}.

W~niniejszej pracy analizowana jest komunikacja synchroniczna na~granicy aplikacji przeglądarkowej i~usług backendowych. Jej wybór wynika z~charakteru badanych operacji, w~których użytkownik oczekuje na~odpowiedź po~wysłaniu żądania.

%----------------------------------------------------------------------

\section{Komunikacja synchroniczna}
\label{sec:KomunikacjaSynchroniczna}

%----------------------------------------------------------------------

Komunikacja synchroniczna opiera się na~modelu żądanie--odpowiedź, w~którym nadawca wysyła żądanie do~odbiorcy i~oczekuje na~jego przetworzenie oraz zwrócenie odpowiedzi. Model ten obowiązuje zarówno w~komunikacji pomiędzy aplikacjami internetowymi a~usługami backendowymi, jak i~pomiędzy samymi mikroserwisami.
W~ekosystemie .NET realizują go dwa mechanizmy omawiane w~dalszych sekcjach: styl REST oraz zdalne wywoływanie procedur w~postaci frameworka gRPC.

\section{REST API w~ASP.NET Core}
\label{sec:RESTAPI}

%----------------------------------------------------------------------

\textit{Representational State Transfer} (REST) to~styl architektoniczny sformalizowany przez Roya Fieldinga~\cite{bib:Fielding2000}, definiujący zestaw reguł dla rozproszonych systemów hipermedialnych. W~architekturze mikroserwisowej REST pozostaje domyślnym wyborem dla komunikacji synchronicznej, ponieważ opiera się wyłącznie na~mechanizmach samego protokołu HTTP i~nie wymaga dodatkowej warstwy narzędziowej po~żadnej ze~stron~\cite{bib:Newman2021, bib:Fowler2014}. Operacje wykonywane są~metodami HTTP (GET, POST, PUT, DELETE) na~zasobach identyfikowanych przez URI, a~ich reprezentację stanowi zwykle format JSON.

Fielding zdefiniował sześć podstawowych ograniczeń stylu REST: architekturę klient--serwer, bezstanowość, buforowalność odpowiedzi, warstwowość systemu, opcjonalny kod na~żądanie oraz jednolity interfejs~\cite{bib:Fielding2000}. W~praktyce inżynierskiej kluczowy element jednolitego interfejsu, jakim jest sterowanie stanem aplikacji przez hipermedia (HATEOAS), bywa pomijany na~rzecz prostszego modelu żądanie--odpowiedź.

Styl REST nie jest powiązany z~konkretną wersją protokołu HTTP: te~same punkty końcowe mogą być udostępniane po~HTTP/1.1 oraz po~HTTP/2. Wersja protokołu stanowi więc zmienną niezależną od~formatu danych: porównanie REST z~gRPC obejmuje oba te~wymiary równocześnie, o~ile nie zostaną rozdzielone w~projekcie eksperymentu. W~systemie zrealizowanym na~potrzeby pracy ścieżka REST działa po~HTTP/1.1.

W~środowisku .NET interfejsy REST API mogą być implementowane za~pomocą platformy ASP.NET Core. Framework udostępnia model \textit{Minimal API}~\cite{bib:MinimalApi}, umożliwiający definiowanie punktów końcowych bez konieczności stosowania kontrolerów. Listing~\ref{lst:RESTMinimal} przedstawia przykładową implementację asynchronicznego pobierania rekordu, odpowiadającą rozwiązaniu przyjętemu w~usłudze katalogu produktów opisanej w~rozdziale~\ref{cha:StudiumPrzypadku}.

\begin{lstlisting}[language={[Sharp]C}, caption={Definicja punktu końcowego REST z~wykorzystaniem Minimal API w~.NET~10}, label=lst:RESTMinimal]
app.MapGet("/api/products/{id}", async (ProductDbContext db, string id) =>
{
    var product = await db.Products
        .AsNoTracking()
        .FirstOrDefaultAsync(p => p.Id == id);
        
    return product is null ? Results.NotFound() : Results.Ok(product);
});
\end{lstlisting}

Brak stanu sesji po~stronie usługi pozwala kierować kolejne żądania tego~samego klienta do~dowolnej instancji, a~nagłówki \texttt{Cache-Control} oraz \texttt{ETag} umożliwiają buforowanie odpowiedzi w~warstwie sieciowej bez udziału kodu aplikacji. Reprezentacja tekstowa pozostaje czytelna dla człowieka, więc do~diagnostyki wystarcza podgląd ruchu HTTP, przy czym nazwy pól powtarzane są~w~każdym rekordzie odpowiedzi. Opis interfejsu, na~przykład w~postaci specyfikacji OpenAPI, powstaje obok implementacji, dlatego niezgodności kontraktu ujawniają się podczas wykonania.

\section{Architektura i~implementacja gRPC}
\label{sec:gRPC}

%----------------------------------------------------------------------

Odmienne założenia przyjmuje gRPC, udostępniony przez Google jako projekt otwarty w~2015~roku~\cite{bib:gRPCDocs}. Zamiast operacji na~zasobach klient wywołuje zdalną procedurę o~zadeklarowanej sygnaturze, argumenty i~wynik przenoszone są~w~formacie binarnym Protocol Buffers, a~transport zapewnia protokół HTTP/2. Połączenie tych trzech decyzji zmniejsza objętość komunikatów oraz koszt ich przetwarzania, co~czyni gRPC rozwiązaniem stosowanym w~komunikacji pomiędzy usługami wewnątrz systemu.

Centralnym elementem gRPC jest kontrakt definiowany za~pomocą języka Protocol Buffers, określający typy danych oraz operacje dostępne w~usłudze \cite{bib:ProtocolBuffers}. Definicja zapisana w~pliku \texttt{.proto} może zostać wykorzystana do~automatycznej generacji kodu klienta i~serwera. Przykładową definicję serwisu przedstawiono na~listingu~\ref{lst:gRPCProto}.

\begin{lstlisting}[language=Protobuf, caption={Definicja serwisu gRPC w~formacie Protocol Buffers}, label=lst:gRPCProto]
syntax = "proto3";

package product;

service ProductService {
  rpc GetProduct (ProductRequest) returns (ProductResponse);
}

message ProductRequest {
  string id = 1;
}

message ProductResponse {
  string id = 1;
  string name = 2;
  double price = 3;
}
\end{lstlisting}

\begin{sloppypar}
W~ekosystemie .NET obsługę gRPC zapewnia pakiet \texttt{Grpc.AspNetCore}, integrujący framework z~platformą ASP.NET~Core. Wykorzystywany transport HTTP/2 multipleksuje równoległe wywołania w~jednym połączeniu TCP i~udostępnia kontrolę przepływu na~poziomie pojedynczego strumienia~\cite{bib:RFC9113}, a~kompresja nagłówków algorytmem HPACK ogranicza objętość metadanych powtarzanych w~kolejnych żądaniach~\cite{bib:RFC7541}. W~połączeniu z~binarną serializacją Protocol Buffers pozwala to~zmniejszyć rozmiar komunikatów w~porównaniu z~formatem JSON.
\end{sloppypar}
