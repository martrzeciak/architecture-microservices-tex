\chapter{Mechanizmy komunikacji w~architekturze mikroserwisowej}

\label{cha:MechanizmyKomunikacji}

Jak przedstawiono w~rozdziale~\ref{cha:WprowadzenieDoMikroserwisow}, architektura mikroserwisowa zakłada podział systemu na~niezależne usługi odpowiedzialne za~określone obszary funkcjonalne. Każdy mikroserwis funkcjonuje jako odrębny proces, co~sprawia, że~realizacja złożonych procesów biznesowych wymaga komunikacji pomiędzy poszczególnymi usługami. Wybór odpowiedniego mechanizmu wymiany danych ma~istotne znaczenie dla wydajności, skalowalności i~niezawodności całego systemu~\cite{bib:Richardson2018}.

Mechanizmy komunikacji stosowane w~architekturze mikroserwisowej można podzielić ze~względu na~sposób wymiany danych na~komunikację synchroniczną oraz asynchroniczną. W~pierwszym przypadku usługa oczekuje na~odpowiedź w~ramach obsługi żądania, natomiast w~drugim wymiana danych odbywa się niezależnie od~bezpośredniej odpowiedzi odbiorcy, najczęściej za~pośrednictwem brokera wiadomości. Oba podejścia znajdują zastosowanie w~różnych scenariuszach i~charakteryzują się odmiennymi właściwościami.


%----------------------------------------------------------------------

\section{Komunikacja asynchroniczna}

\label{sec:KomunikacjaAsynchroniczna}

%----------------------------------------------------------------------

Komunikacja asynchroniczna zakłada rozdzielenie momentu wysłania wiadomości od~jej przetworzenia przez odbiorcę. Nadawca nie musi oczekiwać na~bezpośrednią odpowiedź usługi, a~wiadomość może zostać przechowana przez pośredniczący broker i~przetworzona w~późniejszym czasie. Podejście to~ogranicza bezpośrednie zależności pomiędzy usługami oraz umożliwia niezależne przetwarzanie wiadomości w~warunkach zmiennego obciążenia.
W~ekosystemie .NET komunikacja asynchroniczna może być realizowana z~wykorzystaniem brokerów wiadomości oraz bibliotek zapewniających abstrakcję nad ich obsługą.

\section{Komunikacja synchroniczna}
\label{sec:KomunikacjaSynchroniczna}

%----------------------------------------------------------------------

Komunikacja synchroniczna opiera się na~modelu żądanie--odpowiedź, w~którym nadawca wysyła żądanie do~odbiorcy i~oczekuje na~jego przetworzenie oraz zwrócenie odpowiedzi. Podejście to~jest powszechnie stosowane zarówno w~komunikacji pomiędzy aplikacjami internetowymi a~usługami backendowymi, jak i~pomiędzy mikroserwisami.
W~ekosystemie .NET komunikacja synchroniczna może być realizowana z~wykorzystaniem różnych mechanizmów, w~tym stylu REST oraz mechanizmów RPC.

\subsection{REST API w~ASP.NET Core}
\label{subsec:RESTAPI}

\textit{Representational State Transfer} (REST) to~styl architektoniczny sformalizowany przez Roya Fieldinga~\cite{bib:Fielding2000}, definiujący zestaw reguł dla rozproszonych systemów hipermedialnych. W~architekturze mikroserwisowej REST stanowi najpowszechniejszy mechanizm komunikacji synchronicznej ze~względu na~prostotę, uniwersalność oraz dojrzałość ekosystemu narzędziowego~\cite{bib:Newman2021, bib:Fowler2014}. Opiera się na~wykorzystaniu metod protokołu HTTP (GET, POST, PUT, DELETE) do~operacji na~zasobach identyfikowanych przez URI, których reprezentację najczęściej stanowi format JSON.

Fielding zdefiniował sześć podstawowych ograniczeń stylu REST: architekturę klient--serwer, bezstanowość, buforowalność odpowiedzi, warstwowość systemu, opcjonalny kod na~żądanie oraz jednolity interfejs~\cite{bib:Fielding2000}. W~praktyce inżynierskiej kluczowy element jednolitego interfejsu, jakim jest sterowanie stanem aplikacji przez hipermedia (HATEOAS), bywa pomijany na~rzecz prostszego modelu żądanie--odpowiedź.

W~środowisku .NET interfejsy REST API mogą być implementowane za pomocą platformy ASP.NET Core. Framework udostępnia między innymi model \textit{Minimal API}~\cite{bib:MinimalApi}, umożliwiający definiowanie punktów końcowych bez konieczności stosowania kontrolerów. Listing~\ref{lst:RESTMinimal} przedstawia przykładową implementację asynchronicznego pobierania rekordu.

\begin{lstlisting}[language={[Sharp]C}, caption={Definicja punktu końcowego REST z~wykorzystaniem Minimal API w~.NET~10}, label=lst:RESTMinimal]
app.MapGet("/api/products/{id}", async (ProductDbContext db, string id) =>
{
    var product = await db.Products
        .AsNoTracking()
        .FirstOrDefaultAsync(p => p.Id == id);
        
    return product is null ? Results.NotFound() : Results.Ok(product);
});
\end{lstlisting}

Do~głównych zalet stylu REST należą bezstanowość ułatwiająca skalowanie horyzontalne, natywna obsługa buforowania odpowiedzi w~infrastrukturze sieciowej oraz czytelność formatu JSON. Do~ograniczeń zalicza się narzut objętościowy danych tekstowych, brak ścisłego kontraktu binarnego oraz zjawisko nadmiernej komunikacji (ang.\ \textit{chatty API}).

\section{gRPC -- architektura i~implementacja}
\label{subsec:gRPC}

gRPC to~framework komunikacji wykorzystujący protokół HTTP/2 oraz format serializacji Protocol Buffers, opracowany przez Google i~udostępniony jako projekt open-source w~2015~roku \cite{bib:gRPCDocs}. W~porównaniu do~REST wykorzystuje binarną serializację danych oraz mechanizmy HTTP/2, w~tym multipleksowanie wielu wywołań w~ramach jednego połączenia TCP. Z~tego względu jest często stosowany w~komunikacji pomiędzy mikroserwisami, gdzie istotne są~wydajność i~niskie opóźnienia.

Centralnym elementem gRPC jest kontrakt definiowany za~pomocą języka Protocol Buffers, określający typy danych oraz operacje dostępne w~usłudze \cite{bib:ProtocolBuffers}. Definicja zapisana w~pliku \texttt{.proto} może zostać wykorzystana do~automatycznej generacji kodu klienta i~serwera. Przykładową definicję serwisu przedstawiono na~listingu~\ref{lst:gRPCProto}.

\begin{lstlisting}[caption={Definicja serwisu gRPC w~formacie Protocol Buffers}, label=lst:gRPCProto]
syntax = "proto3";

package product;

service ProductService {
  rpc GetProduct (ProductRequest) returns (ProductResponse);
  rpc StreamProducts (ProductRequest) returns (stream ProductResponse);
}

message ProductRequest {
  string id = 1;
}

message ProductResponse {
  string id = 1;
  string name = 2;
  double price = 3;
}
\end{lstlisting}

\begin{sloppypar}
W~ekosystemie .NET obsługa gRPC jest dostępna za~pośrednictwem pakietu \texttt{Grpc.AspNetCore}, który integruje framework z~platformą ASP.NET~Core. HTTP/2 zapewnia między innymi multipleksowanie wielu strumieni oraz kontrolę przepływu \cite{bib:RFC9113}. Kompresja nagłówków za~pomocą algorytmu HPACK dodatkowo ogranicza ilość przesyłanych danych \cite{bib:RFC7541}. W~połączeniu z~binarną serializacją Protocol Buffers pozwala to~zmniejszyć rozmiar komunikatów w~porównaniu z~formatem JSON.
\end{sloppypar}
