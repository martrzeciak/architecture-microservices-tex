\chapter{Porównawcza analiza wydajności REST i~gRPC-Web}
\label{cha:AnalizaWydajnosci}

Niniejszy rozdział przedstawia wyniki eksperymentu przeprowadzonego zgodnie z~metodologią opisaną w~rozdziale~\ref{cha:MetodologiaBadan}. Analiza rozpoczyna się od~wielkości niezależnych od~warunków sieciowych: wolumenu przesyłanych danych oraz wynikającego z~niego modelu liczby wymian pakietów. Dopiero one pozwalają zinterpretować zmierzone czasy odpowiedzi. Następnie omówione zostają kolejno scenariusze Echo, Products i~Orders, rozdzielenie wpływu serializacji od~wpływu wersji protokołu HTTP, granica przepustowości stanowiska pomiarowego, powtarzalność wyników wraz z~przedziałami ufności wyznaczonymi dla zmierzonych różnic oraz mechanizmy kontrolne potwierdzające wiarygodność uzyskanych rezultatów. Rozdział zamyka weryfikacja hipotez oraz rekomendacje architektoniczne wraz z~wytycznymi wdrożeniowymi.

\subsection{Wpływ kompresji treści na~wolumen danych}
\label{subsec:Kompresja}

Wszystkie rozmiary przedstawione w~tabeli~\ref{tab:WolumenDanych} dotyczą treści nieskompresowanej. W~badanym systemie kompresja ciała odpowiedzi nie została włączona na~żadnej ze~ścieżek: usługi nie korzystają z~oprogramowania pośredniczącego kompresji, a~konfiguracja serwera pośredniczącego nie zawiera filtra kompresora. W~takim przypadku żaden z~badanych wariantów nie jest uprzywilejowany. Odpowiada on~przy tym domyślnym ustawieniom platformy ASP.NET Core oraz szkieletu gRPC dla~.NET. Konsekwencje tego wyboru dla zakresu wniosków wymagają jednak omówienia, ponieważ w~praktyce wdrożeniowej dokumenty JSON podawane są~najczęściej z~kompresją realizowaną przez serwer aplikacyjny, odwrotne proxy lub sieć dostarczania treści.

Wpływ kompresji oszacowano ilościowo dla scenariusza Echo, którego ładunek generowany jest w~sposób deterministyczny. Poprawność odtworzenia zweryfikowano przez porównanie z~rozmiarami zmierzonymi na~wdrożonym systemie: dla 200~rekordów uzyskano 36\,246~B wobec zmierzonych 36\,242~B w~formacie JSON oraz 24\,079~B wobec 24\,104~B w~formacie binarnym, czyli odchylenie nieprzekraczające 0,1\%. \section{Model liczby wymian pakietów}
\label{sec:ModelOkna}
% -----------------------------------------------------------------------

Zmierzona charakterystyka łącza (sekcja~\ref{subsec:CharakterystykaLacza}) ujawniła, że~przepustowość pojedynczego połączenia wynosi około 20~Mbit/s, mimo że~przepustowość zagregowana przekracza 270~Mbit/s. Iloczyn przepustowości i~opóźnienia dla tego połączenia wynosi

\begin{equation}
20~\mathrm{Mbit/s} \cdot 0{,}0262~\mathrm{s} \approx 65\,500~\mathrm{B} \approx 64~\mathrm{KiB},
\label{eq:BDP}
\end{equation}

co~odpowiada rozmiarowi okna odbiorczego protokołu TCP bez~zastosowania skalowania okna~\cite{bib:RFC9293}. Przy oknie mniejszym od~iloczynu przepustowości i~opóźnienia przepustowość osiągalna w~jednym połączeniu wynika z~rozmiaru okna, nie z~pojemności łącza. Czynnikiem ograniczającym pojedyncze żądanie nie jest zatem pojemność łącza, lecz ilość danych, jaką nadawca może wysłać przed otrzymaniem potwierdzenia: po~wypełnieniu okna transmisja wstrzymuje się do~nadejścia potwierdzenia od~odbiorcy.

Zgodność wartości 64~KiB z~iloczynem przepustowości i~opóźnienia nie jest
dowodem, lecz przesłanką: obie wielkości powiązane są~tożsamością
$B = W / \mathrm{RTT}$: tym~samym równaniem co~w~równaniu~(\ref{eq:BDP}),
zapisanym względem~$B$ zamiast~$W$, a~wyznaczenie jednej z~drugiej
stanowi jedynie przeliczenie. Rozstrzygające jest natomiast to, że~wielkość ta~przewiduje niezależnie zmierzone czasy odpowiedzi dla ładunków o~różnym rozmiarze, co~wykazano w~dalszej części sekcji. Należy przy tym zaznaczyć, że~identyczny schodkowy przebieg dawałby mechanizm powolnego startu protokołu TCP, w~którym okno zatoru narasta w~kolejnych obiegach pakietu. Rozstrzygnięcie, który z~obu mechanizmów jest tu~czynnikiem wiodącym, wymagałoby przechwycenia ruchu na~poziomie pakietów, czego nie wykonano, dla wniosków pracy jest to~jednak bez znaczenia, ponieważ oba prowadzą do~tego~samego przewidywania: koszt transmisji rośnie skokowo, o~wielokrotność opóźnienia obiegu pakietu, wraz z~przekraczaniem kolejnych wielokrotności rozmiaru okna.

Z~zależności tej wynika model przewidujący czas transmisji odpowiedzi. Przesłanie odpowiedzi o~rozmiarze $s$ wymaga $\lceil s / 64~\mathrm{KiB} \rceil$ okien, a~każde okno ponad pierwsze kosztuje jedno dodatkowe opóźnienie obiegu pakietu. Przewidywana liczba dodatkowych obiegów wynosi zatem

\begin{equation}
n_{\mathrm{RTT}} = \left\lceil \frac{s}{64~\mathrm{KiB}} \right\rceil - 1.
\label{eq:WindowModel}
\end{equation}

Model ten poddano weryfikacji ilościowej, przyjmując za~punkt odniesienia konfigurację o~200~rekordach, w~której odpowiedź obu formatów mieści się w~jednym oknie. Nadwyżkę czasu względem tego punktu odniesienia podzielono przez zmierzone opóźnienie obiegu pakietu (26,2~ms). Wyniki przedstawia tabela~\ref{tab:WeryfikacjaModelu}.

Model wyjaśnia w~szczególności zjawisko, którego nie sposób wyjaśnić samą przepustowością: różnica 30~kilobajtów pomiędzy formatami przy 500~rekordach scenariusza Echo odpowiadałaby przy przepustowości zagregowanej niespełna jednej milisekundy, a~przy przepustowości pojedynczego strumienia, około dwunastu milisekund, natomiast zmierzona różnica wynosi 26~ms, czyli dokładnie jeden obieg pakietu.

Przewaga serializacji binarnej nie jest ciągłą funkcją rozmiaru odpowiedzi, lecz realizuje się skokowo: wyłącznie wtedy, gdy mniejszy ładunek wymaga mniejszej liczby okien. Ponadto wielkość tej przewagi jest proporcjonalna do~opóźnienia łącza, nie do~szybkości serwera: w~sieci lokalnej, gdzie opóźnienie obiegu pakietu jest mniejsze od~milisekundy, ten~sam mechanizm dawałby korzyść pomijalną.

porównawczego. Do~izolowania wpływu protokołu służy scenariusz Echo,
natomiast do~oceny zachowania w~warunkach realnych -- scenariusz
z~ciepłą pamięcią podręczną.

\section{Rozdzielenie wpływu serializacji od~wpływu wersji protokołu HTTP}

Wielkość efektu jest zatem porównywalna z~niepewnością jego oszacowania, co~stanowi uzasadnienie wniosku o~drugorzędnym znaczeniu wyboru pomiędzy wariantem bezpośrednim a~wariantem z~proxy.

Po~czwarte, w~scenariuszach zapisu żadna z~różnic nie jest rozstrzygnięta. Przedziały są~w~tej grupie od~kilku do~kilkudziesięciu razy szersze niż w~odczycie. Jedyny wyjątek dotyczy pary Envoy--Direct przy pięćdziesięciu pozycjach i~dwudziestu klientach ($-59{,}1 \pm 45{,}2$~ms), lecz znak tej różnicy jest przeciwny niż w~pozostałych komórkach tej grupy, a~jej wartość wynika z~jednego odstającego przebiegu. Obserwacji tej nie można zatem interpretować jako właściwości protokołu.

\section{Weryfikacja hipotez badawczych}
\label{sec:WeryfikacjaHipotez}
% -----------------------------------------------------------------------

\begin{sloppypar}
\textbf{H1 (warianty gRPC-Web osiągają niższe opóźnienie niż REST, a~przewaga rośnie z~rozmiarem odpowiedzi):} hipoteza potwierdzona z~zastrzeżeniem dotyczącym charakteru zależności. Przewaga występuje i~jest znaczna: 26--43\% przy odpowiedziach od~500~rekordów. Zależność od~rozmiaru odpowiedzi nie jest jednak ciągła, jak zakładano, lecz skokowa: ujawnia się dopiero po~przekroczeniu rozmiaru okna odbiorczego, a~w~zakresie do~200~rekordów pozostaje w~granicach kilku procent. Poprawne sformułowanie hipotezy musi zatem odnosić się nie do~rozmiaru odpowiedzi jako takiego, lecz do~liczby okien niezbędnych do~jej przesłania.
\end{sloppypar}

\begin{sloppypar}
\textbf{H2 (przy małych odpowiedziach różnice są~nieistotne):} hipoteza potwierdzona. Przy odpowiedziach do~200~rekordów różnice wynoszą od~jednego do~szesnastu procent, przy wartościach bezwzględnych od~jednej do~pięciu milisekund, wobec opóźnienia obiegu pakietu wynoszącego 26,2~ms. Samo opóźnienie propagacji stanowi w~tym zakresie od~około pięćdziesięciu
siedmiu procent czasu odpowiedzi przy dwudziestu równoległych klientach
i~dwustu rekordach do~siedemdziesięciu ośmiu procent przy dziesięciu
klientach i~dziesięciu rekordach. Właściwym wnioskiem jest zatem nie tyle brak różnicy, ile jej praktyczna nieistotność.
\end{sloppypar}

\begin{sloppypar}
\textbf{H3 (przewaga wynika z~redukcji wolumenu danych, nie z~wersji protokołu HTTP):} wyniki wspierają hipotezę. W~dekompozycji przedstawionej w~sekcji~\ref{sec:Dekompozycja} różnica REST--Envoy stanowi około 85--98\% różnicy REST--Direct, w~tym około 95\% dla 500~produktów i~dziesięciu klientów. Są~to udziały w~całkowitym skróceniu czasu. Procenty w~tabeli~\ref{tab:Dekompozycja} odnoszą się natomiast do~czasu REST. Porównanie obejmuje kompletne ścieżki obsługi żądań, dlatego podział ten stanowi przybliżenie udziału serializacji i~transportu.
\end{sloppypar}

\begin{sloppypar}
\textbf{H4 (w~operacjach zapisu różnice zanikają):} nie wykryto stałej przewagi jednego wariantu, ale wyniki nie wystarczają do~potwierdzenia równoważności protokołów. Przy dziesięciu i~pięćdziesięciu pozycjach zamówienia mediany wynoszą 83,5--165,8~ms. Przedziały ufności dla różnic REST--Direct obejmują zero, a~dla pary Envoy--Direct występuje wyjątek omówiony w~sekcji~\ref{sec:PrzedzialyUfnosci}. Udział transakcji bazodanowej i~zmienność wyników ograniczają możliwość rozstrzygnięcia hipotezy.
\end{sloppypar}

\textbf{H5 (wariant Direct osiąga niższe opóźnienie niż wariant z~proxy Envoy):} wyniki częściowo wspierają hipotezę. Wariant bezpośredni ma~niższą medianę w~każdej konfiguracji odczytu z~ciepłą pamięcią podręczną oraz scenariusza Echo. Skrócenie czasu wynosi około 0,4--9,2\%, licząc względem mediany Envoy jako $(T_{\mathrm{Envoy}}-T_{\mathrm{Direct}})/T_{\mathrm{Envoy}}$. Nie wszystkie różnice są~jednak rozstrzygnięte statystycznie. W~grupie scenariuszy z~zimną pamięcią podręczną relacja ta~nie zachodzi konsekwentnie. Wybór wariantu wdrożenia wymaga uwzględnienia również topologii systemu.

\section{Rekomendacje i~wytyczne wdrożeniowe}
\label{sec:RekomendacjeArchitektoniczne}
% -----------------------------------------------------------------------

Uzyskane wyniki nie uzasadniają bezwarunkowego zastąpienia REST przez gRPC-Web. Wskazują natomiast mierzalne kryteria, na~podstawie których można dobrać mechanizm komunikacji do~charakterystyki konkretnego systemu. Decyzja powinna wynikać z~rozmiaru przesyłanych danych, parametrów łącza, dominującego rodzaju operacji oraz wymagań eksploatacyjnych.

\subsection{Rekomendacje architektoniczne}

\begin{enumerate}
    \item \textbf{Rozmiar odpowiedzi należy oceniać względem efektywnego okna transmisji.} Zastosowanie formatu binarnego przynosi istotną korzyść wtedy, gdy zmniejszenie wolumenu ogranicza liczbę wymian pakietów. W~badanym środowisku efekt pojawiał się przy nieskompresowanych odpowiedziach od~około 500~rekordów i~osiągał 26--43\%. Dla małych odpowiedzi różnice pozostawały na~poziomie pojedynczych milisekund, dlatego sam wybór gRPC-Web nie powinien być traktowany jako uniwersalna optymalizacja.

    \item \textbf{Przed zmianą protokołu należy zmierzyć ładunek po~kompresji.} Kompresja gzip zmniejszyła w~oszacowaniu przewagę objętościową Protocol Buffers z~około 33\% do~15--18\% i~sprowadziła wszystkie analizowane odpowiedzi poniżej rozmiaru jednego okna. W~systemach podających dokumenty JSON z~kompresją właściwym pierwszym krokiem jest zatem pomiar rzeczywistego rozmiaru odpowiedzi, a~następnie test opóźnienia w~docelowej sieci. Jeżeli ładunek nadal przekracza próg jednego okna, należy rozważyć również paginację, ograniczenie pól odpowiedzi lub zmianę sposobu agregacji danych.

    \item \textbf{Charakter operacji jest ważniejszy niż sam format komunikatu.} W~odczycie dużych zbiorów koszt transmisji może dominować i~uzasadniać zastosowanie gRPC-Web. W~operacjach zapisu angażujących transakcję bazodanową różnice pomiędzy protokołami nie były rozstrzygalne, ponieważ czas odpowiedzi wyznaczała warstwa persystencji. W~takich ścieżkach priorytetem powinny być optymalizacja zapytań, zakres transakcji i~organizacja zapisu, natomiast protokół należy dobierać ze~względu na~kontrakt, interoperacyjność i~koszt utrzymania.

    \item \textbf{Wybór pomiędzy wariantem bezpośrednim a~proxy powinien wynikać z~topologii systemu.} W~scenariuszach Echo i~odczytu z~ciepłą pamięcią podręczną Direct skracał medianę czasu względem Envoy o~około 0,4--9,2\%, przy czym nie wszystkie różnice były rozstrzygnięte statystycznie. Obsługa bezpośrednia upraszcza ścieżkę żądania i~ogranicza liczbę komponentów, natomiast serwer pośredniczący może być uzasadniony, gdy architektura wymaga wspólnej warstwy routingu i~centralnej konfiguracji ruchu. Nie należy rezygnować z~proxy wyłącznie na~podstawie oczekiwania znaczącego skrócenia czasu odpowiedzi.

    \item \textbf{Pamięć podręczna powinna być traktowana również jako mechanizm stabilizacji czasu odpowiedzi.} W~scenariuszach z~ciepłą pamięcią podręczną współczynnik zmienności wynosił typowo 2--6\%, natomiast przy wymuszonym dostępie do~bazy wzrastał do~10--30\%, a~maksymalnie do~51,3\%. Cache-Aside poprawia więc nie tylko wartość centralną opóźnienia, lecz także jego przewidywalność. Wymaga to~jednocześnie jawnej polityki unieważniania danych oraz osobnego monitorowania ścieżek trafienia i~chybienia.
\end{enumerate}

\subsection{Wytyczne wdrożeniowe}

\begin{enumerate}
    \item \textbf{Test wydajnościowy należy prowadzić w~warunkach odpowiadających docelowemu wdrożeniu.} Powinien on~obejmować rzeczywistą przeglądarkę, końcową konfigurację TLS, kompresji i~serwerów pośredniczących oraz reprezentatywne opóźnienie sieci. Pomiar wyłącznie wewnątrz centrum danych może ukryć efekt zależny od~liczby obiegów pakietu, natomiast test bez kompresji może zawyżyć przewagę formatu binarnego względem konfiguracji produkcyjnej.

    \item \textbf{Należy oddzielić ograniczenia systemu od~ograniczeń generatora obciążenia.} Wspólny pułap przepustowości wszystkich protokołów ujawnił w~badaniu nasycenie stanowiska klienckiego. Przed interpretacją wyników trzeba więc wykonać pomiar skalowania i~wyznaczyć punkt przegięcia. Badania większej współbieżności powinny wykorzystywać wiele maszyn generujących ruch, przy zachowaniu pomiaru czasu wewnątrz strony i~kontroli obciążenia każdej z~nich.

    \item \textbf{Porównywane ścieżki muszą zachowywać symetrię funkcjonalną.} Powinny wykonywać tę~samą logikę biznesową, korzystać z~tych~samych danych i~kończyć pomiar w~tym~samym punkcie cyklu renderowania. Należy też pomiarowo potwierdzić negocjowaną wersję HTTP, liczbę połączeń, rozmiar odpowiedzi i~stan pamięci podręcznej. Bez tej kontroli wynik może opisywać różnicę implementacji, a~nie protokołu.

    \item \textbf{Warstwę obserwowalności należy wykorzystać do~weryfikacji przyczyn, nie jako zamiennik pomiaru klienckiego.} Metryki serwerowe powinny obejmować co~najmniej czas obsługi żądania, liczbę żądań, wykorzystanie zasobów oraz zachowanie środowiska uruchomieniowego. Ich zestawienie z~czasem mierzonym w~przeglądarce pozwala rozróżnić koszt przetwarzania po~stronie usługi od~transmisji, deserializacji i~aktualizacji interfejsu.

    \item \textbf{Decyzję protokołową należy okresowo ponawiać po~zmianach systemu.} Zmiana modelu odpowiedzi, poziomu kompresji, lokalizacji użytkowników, konfiguracji proxy lub sposobu korzystania z~pamięci podręcznej może przesunąć granicę, przy której format binarny daje korzyść. Kryterium wdrożeniowym powinien być zatem wynik powtarzalnego testu dla reprezentatywnych scenariuszy, a~nie właściwość przypisana protokołowi niezależnie od~kontekstu.
\end{enumerate}
