\section{Przegląd badań porównawczych}
\label{sec:StanBadan}

Do~przeglądu wybrano prace empiryczne porównujące REST z~gRPC lub GraphQL. Uwzględniono publikacje, w~których podano środowisko wykonania, rodzaj obciążenia oraz co~najmniej jedną miarę wydajności, taką jak czas odpowiedzi, rozmiar komunikatu albo wykorzystanie zasobów. Zestawienie służy określeniu, które elementy komunikacji zostały już zbadane i~czy uzyskane wyniki można odnieść do~aplikacji działającej w~przeglądarce.

\subsection{Wyniki badań REST i~gRPC}

Wyniki dotychczasowych porównań nie wskazują protokołu, który byłby szybszy w~każdym rodzaju operacji. Niswar i~współautorzy~\cite{bib:Niswar2024} odnotowali najkrótsze czasy odpowiedzi dla gRPC w~mikroserwisach napisanych w~Go. Śliwa i~Pańczyk~\cite{bib:SliwaPanczyk2021}, badający implementacje .NET~5.0, uzyskali korzystne wyniki REST w~wielu scenariuszach, mimo mniejszego wolumenu danych przesyłanego przez gRPC. Z~kolei eksperymenty Bolanowskiego i~współautorów~\cite{bib:Bolanowski2022} oraz Kamińskiego i~współautorów~\cite{bib:Kaminski2023} pokazały, że~wynik zmienia się wraz z~typem danych, operacją i~konfiguracją transportu.

Rozbieżności pomiędzy wynikami można częściowo wyjaśnić konstrukcją eksperymentów. Wraz ze~zmianą protokołu zmieniały się zwykle format reprezentacji, wersja HTTP, biblioteka serwerowa, a~czasem również sposób dostępu do~danych. Mierzono więc kompletne warianty implementacyjne, a~nie wyizolowany koszt protokołu. Różnił się także punkt zakończenia pomiaru. JMeter i~k6 rejestrują obsługę żądania przez klienta testowego, lecz nie uwzględniają deserializacji w~kodzie aplikacji frontendowej ani aktualizacji interfejsu użytkownika.

Badania dotyczące GraphQL pomagają oddzielić wpływ protokołu od~wpływu zakresu odpowiedzi. Brito, Mombach i~Valente~\cite{bib:Brito2019} wykazali, że~migracja klientów API z~REST do~GraphQL może znacznie ograniczyć liczbę zwracanych pól i~rozmiar odpowiedzi. Jest to~korzyść wynikająca z~doboru danych przez klienta, a~nie z~binarnych właściwości reprezentacji. Vadlamani i~współautorzy~\cite{bib:Vadlamani2021} otrzymali wyniki zależne od~konkretnego zapytania do~API GitHuba. W~badaniu Jina i~współautorów~\cite{bib:Jin2025} na~wynik wpływała również odmienna infrastruktura wdrożeniowa porównywanych rozwiązań. Publikacje te~potwierdzają, że~porównywane ścieżki powinny zwracać ten sam zakres informacji i~wykonywać tę~samą logikę biznesową.

\subsection{Zakres i~kryteria analizy}

Przegląd obejmuje publikacje empiryczne, w~których opisano środowisko wykonania, rodzaj obciążenia i~co~najmniej jedną miarę wydajności: czas odpowiedzi, wolumen danych albo wykorzystanie zasobów. Dokumentacje techniczne wykorzystano wyłącznie do~wyjaśnienia mechanizmów implementacyjnych. Nie stanowią one samodzielnego dowodu przewagi wydajnościowej jednego rozwiązania nad drugim.

Przy interpretacji prac rozpatrywano przede wszystkim granicę pomiaru, użyte środowisko, funkcjonalną równoważność operacji oraz sposób dostępu do~danych. Generator obciążenia rejestruje czas obsługi wywołania API, podczas gdy pomiar realizowany w~przeglądarce obejmuje dodatkowo odebranie odpowiedzi, jej dekodowanie oraz aktualizację interfejsu. Te~wartości odpowiadają odmiennym pytaniom badawczym i~nie powinny być traktowane jako zamienne.

\subsection{Porównania REST i~gRPC}

Śliwa i~Pańczyk~\cite{bib:SliwaPanczyk2021} porównali REST, GraphQL i~gRPC w~trzech aplikacjach o~tej samej funkcjonalności, zbudowanych na~platformie .NET~5. W~ich testach REST uzyskał korzystne wyniki czasu odpowiedzi i~przepustowości w~wielu scenariuszach, podczas gdy gRPC przesyłało mniej danych. Pokazuje to, że~mniejszy komunikat nie gwarantuje krótszego czasu całej operacji. Badanie jest istotnym punktem odniesienia ze~względu na~wspólny ekosystem .NET, lecz pomiar generatora obciążenia nie obejmuje aktualizacji DOM.

Bolanowski i~współautorzy~\cite{bib:Bolanowski2022} oraz Kamiński i~współautorzy~\cite{bib:Kaminski2023} zwracają uwagę na~zależność wyników od~rodzaju operacji, środowiska uruchomieniowego i~konfiguracji transportu. W~porównaniach tego rodzaju równocześnie zmieniają się format reprezentacji, wersja HTTP, biblioteka serwerowa, a~niekiedy także ścieżka dostępu do~danych. Wynik dotyczy więc kompletnego wariantu implementacyjnego, a~nie wyizolowanego kosztu pojedynczego protokołu. Wniosek ten ma~bezpośrednie znaczenie dla interpretacji eksperymentu przedstawionego w~niniejszej pracy.

\subsection{GraphQL jako odrębny wymiar porównania}

GraphQL umożliwia klientowi dobór pól odpowiedzi, przez co może zmieniać zarówno objętość danych, jak i~liczbę żądań potrzebnych do~realizacji operacji. Jest to~inna oś optymalizacji niż zastosowanie zwartego kodowania tej samej reprezentacji. Badanie Brito, Mombach i~Valente~\cite{bib:Brito2019} pokazuje, że~ograniczenie zakresu zwracanych pól może istotnie zmniejszyć odpowiedź. Z~kolei Vadlamani i~współautorzy~\cite{bib:Vadlamani2021} nie wskazali rozwiązania szybszego dla każdej analizowanej pary zapytań.

\subsection{Ograniczenia porównywalności i~zakres wkładu pracy}

Natywne gRPC oraz gRPC-Web nie są~zamienne z~perspektywy aplikacji przeglądarkowej. Ograniczenia przeglądarki wymagają odmiennego sposobu realizacji komunikacji~\cite{bib:gRPCWeb,bib:ProtocolWeb}. Ponadto REST nie jest ograniczony do~HTTP/1.1, a~zmiana formatu danych, wersji HTTP, TLS i~obecności proxy prowadzi do~porównania całych ścieżek komunikacji. Pomiar mniejszej odpowiedzi wspiera wyjaśnienie zaobserwowanej różnicy, ale nie wyznacza samodzielnie udziału każdego czynnika.

W~omówionych publikacjach nie przedstawiono łącznego porównania REST, gRPC-Web przez Envoy oraz gRPC-Web obsługiwanego bezpośrednio w~ASP.NET Core, prowadzonego do~momentu aktualizacji DOM i~z~rozróżnieniem rozmiaru odpowiedzi oraz ścieżek dostępu do~danych. Niniejsza praca uzupełnia ten obraz o~powtarzany eksperyment w~systemie .NET~10 i~Angular. Wyniki mają charakter kontekstowy: opisują zachowanie trzech konkretnych konfiguracji, a~nie uniwersalny ranking technologii. GraphQL uwzględniono w~przeglądzie jako alternatywny sposób doboru danych, lecz nie jako wariant eksperymentalny.
