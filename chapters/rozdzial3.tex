\chapter{gRPC-Web i~komunikacja frontend-backend}

\label{cha:gRPCWeb}

Aplikacja działająca w~przeglądarce nie może posłużyć się natywnym gRPC, choć po~stronie usług protokół ten jest w~ekosystemie .NET dostępny bez ograniczeń. Przyczyna leży w~sposobie, w~jaki przeglądarka udostępnia aplikacjom warstwę sieciową: część mechanizmów HTTP/2 wykorzystywanych przez gRPC pozostaje poza zasięgiem kodu wykonywanego na~stronie.

W~konsekwencji opracowano mechanizm gRPC-Web, umożliwiający aplikacjom uruchamianym w~przeglądarce komunikację z~usługami wykorzystującymi gRPC. W~zależności od~zastosowanej implementacji komunikacja ta~może być realizowana za~pośrednictwem serwera pośredniczącego lub bezpośrednio przez warstwę obsługującą gRPC-Web po~stronie usługi. Oba sposoby stanowią warianty porównywane w~eksperymencie, dlatego w~rozdziale omówiono kolejno przyczyny ograniczeń przeglądarki, sposób ramkowania komunikatów w~gRPC-Web oraz realizację klienta w~aplikacji frontendowej.

\section{Ograniczenia natywnego gRPC w~przeglądarkach}

\label{sec:OgraniczeniagRPC}

% -----------------------------------------------------------------------

Protokół gRPC w~swojej natywnej postaci wykorzystuje mechanizmy transportowe HTTP/2, w~tym ramki typu \texttt{HEADERS} przesyłane po~zakończeniu ciała odpowiedzi. Mechanizm ten, określany jako nagłówki końcowe (ang.\ \textit{trailing headers}), służy do~przekazywania metadanych dotyczących statusu wywołania procedury zdalnej po~przesłaniu treści odpowiedzi. Zgodnie ze~specyfikacją gRPC~\cite{bib:gRPCDocs}, status wywołania jest przekazywany za~pomocą metadanych końcowych, w~szczególności nagłówka \texttt{grpc-status}, a~opis błędu może trafić do~nagłówka \texttt{grpc-message}.

Interfejsy dostępne dla kodu wykonywanego na~stronie operują na~kompletnej odpowiedzi HTTP. Ani \textit{Fetch API}, zdefiniowany przez specyfikację WHATWG~\cite{bib:FetchAPI}, ani \textit{XMLHttpRequest} nie sięgają do~warstwy transportowej HTTP/2, wobec czego nagłówki końcowe odpowiedzi pozostają dla aplikacji nieczytelne. Samo połączenie HTTP/2 zostaje wprawdzie zestawione, lecz zarządza nim przeglądarka, decydując o~liczbie połączeń i~multipleksowaniu strumieni bez udziału kodu aplikacji.

\section{Architektura gRPC-Web}

\label{sec:ArchitekturagRPCWeb}

Istotną różnicą pomiędzy natywnym gRPC a~gRPC-Web jest sposób przekazywania informacji o~statusie wywołania. W~natywnym gRPC informacje te~są~przekazywane w~nagłówkach końcowych HTTP/2. W~gRPC-Web zostały one umieszczone w~specjalnej ramce znajdującej się wewnątrz ciała odpowiedzi HTTP. Zgodnie ze~specyfikacją gRPC-Web ramka końcowa jest poprzedzona bajtem flagi o~wartości \texttt{0x80}, a~ramki zawierające właściwe komunikaty oznaczane są~wartością \texttt{0x00}~\cite{bib:ProtocolWeb}.

Takie rozwiązanie pozwala na~przesyłanie komunikatów gRPC z~wykorzystaniem mechanizmów dostępnych dla aplikacji przeglądarkowych. Warstwa gRPC-Web może być obsługiwana bezpośrednio przez serwer aplikacyjny albo przez dedykowany serwer pośredniczący.

Warianty różnią się nie tylko liczbą komponentów na~ścieżce żądania, lecz także warstwą transportową po~stronie przeglądarki. W~wariancie z~serwerem pośredniczącym Envoy, wyposażonym w~filtr \texttt{grpc\_web}, przeglądarka wysyła ramki gRPC-Web po~HTTP/1.1, a~translację na~natywne gRPC po~HTTP/2 wykonuje proxy. W~wariancie \textit{Direct} obsługę gRPC-Web realizuje bezpośrednio aplikacja ASP.NET Core, a~połączenie zestawiane jest po~HTTP/2 w~ramach sesji TLS. Różnica dotyczy równocześnie obecności proxy oraz wersji protokołu HTTP, co~należy uwzględniać przy interpretacji zmierzonych czasów.

\section{Implementacja we~frameworku Angular}

\label{sec:ImplementacjagRPCWeb}

% -----------------------------------------------------------------------

Opisane warianty gRPC-Web wymagają klienta działającego w~rzeczywistym środowisku przeglądarkowym. W~niniejszej pracy rolę tę~pełni aplikacja frontendowa wykorzystująca framework \textit{Angular 20}. Aplikacja odpowiada zarówno za~prezentację danych, jak i~obsługę komunikacji z~backendem. Jej architektura została przygotowana w~taki sposób, aby umożliwić przełączanie pomiędzy badanymi wariantami komunikacji bez zmiany warstwy prezentacji.

Do~obsługi gRPC-Web wykorzystano bibliotekę \textit{Connect RPC} opracowaną przez firmę Buf~\cite{bib:ConnectRPC}. Biblioteka udostępnia klienta gRPC-Web w~postaci modułów ECMAScript i~współpracuje z~generowanym kodem TypeScript. Referencyjna biblioteka \texttt{grpc-web} rozprowadzana jest w~formacie CommonJS, którego pakietowanie w~narzędziu budującym aplikację Angular wymagałoby dodatkowej warstwy zgodności; z~tego powodu w~badanej aplikacji zastosowano Connect RPC.

\section{Generowanie kodu klienckiego}

\label{sec:ConnectRPC}

% -----------------------------------------------------------------------

Komunikacja wykorzystująca gRPC-Web została oparta na~kontrakcie zdefiniowanym w~języku Protocol Buffers. Na~podstawie plików \texttt{.proto} generowany jest kod TypeScript wykorzystywany następnie przez aplikację Angular. W~procesie tym wykorzystano kompilator Protocol Buffers~\cite{bib:ProtoGen} oraz wtyczki \texttt{protoc-gen-es} i~\texttt{protoc-gen-connect-es}. Pierwsza z~nich odpowiada za~generowanie definicji komunikatów, druga za~deskryptory usług wykorzystywane przez bibliotekę Connect RPC.

Listing~\ref{lst:ProtoGenConnect} przedstawia konfigurację generowania kodu klienckiego.

\begin{lstlisting}[
  language=bash,
  caption={Generowanie kodu klienckiego dla Connect RPC},
  label=lst:ProtoGenConnect
]
# Client libraries and generator plugins
npm install @connectrpc/connect @connectrpc/connect-web
npm install --save-dev @bufbuild/protoc-gen-es \
  @connectrpc/protoc-gen-connect-es

# Code generation
grpc_tools_node_protoc \
  --plugin=protoc-gen-es=node_modules/.bin/protoc-gen-es \
  --es_out=src/generated-connect \
  --plugin=protoc-gen-connect-es=node_modules/.bin/protoc-gen-connect-es \
  --connect-es_out=src/generated-connect \
  -I ../../protos \
  ../../protos/product.proto ../../protos/order.proto
\end{lstlisting}

Wywołanie generatora zostało umieszczone w~skrypcie npm, dzięki czemu proces generowania kodu może być wykonywany w~sposób powtarzalny podczas budowania projektu. Podejście to~zapewnia również spójność pomiędzy kontraktem zapisanym w~plikach Protocol Buffers a~kodem wykorzystywanym przez aplikację frontendową.
